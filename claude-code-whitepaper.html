总 核心概念：什么是 Claude Code 和 Harness？

Claude Code 是 Anthropic 推出的终端原生 AI 编程助手。它不仅能生成、解释、优化代码，还能直接操作文件、运行 Shell 命令、管理 Git 版本——它是一个可以真正动手干活的 AI 智能体。

Harness = 工具 + 知识 + 上下文管理 + 权限边界

模型是发动机，Harness 是底盘、变速箱和导航。发动机再好，装在没有方向盘的车上也跑不起来。模型决定上限，Harness 决定你实际能拿到多少。

CLAUDE.md

项目全局约定文件。Claude Code 启动时自动加载，每个对话回合都在上下文里。只放"AI 需要在你开口之前就知道的事"。

规则自动加载

Hooks

生命周期自动触发器。SessionStart 时注入 git 状态，Stop 后自动审查。让 Harness 在正确时机做正确的事。

自动化生命周期

Skills

可复用的工作流知识包。描述 + 指令 + 工具三层结构，延迟加载，按需激活。就像手机上的 App。

可复用延迟加载

Sub-agents

拥有独立上下文的隔离 Claude 实例。派去探索代码库、执行子任务，只返回结果摘要。保护主会话上下文不被撑爆。

隔离上下文管理

LSP

语言服务器协议。符号级搜索，不是字符串匹配。同一个变量名只给你一处定义和两处引用，而不是几百个字符串匹配。

精准代码理解

Plugins

官方/社区打包的组件集合。CLAUDE.md + Hooks + Skills + Sub-agents 打包成一个可安装单元，团队一键部署。

打包分发

🛠️ Claude Code 开箱指南：从安装到首次使用

来源：Claude Code 快速上手指南 (HiddenState) + Anthropic 官方文档 + 菜鸟教程 · 原文链接 ↗

以下是 Claude Code 从零安装到首次上手的完整指南。无论你是 macOS、Linux 还是 Windows 用户，一条命令即可完成安装。

1. 环境准备

平台要求说明
macOS10.15+自带 Terminal，可直接安装
Windows10+ 或 WSLPowerShell 执行安装脚本，自动检测 Git Bash
Linux主流发行版使用 curl + bash 安装
Node.js可选npm 方式安装时需要；官方脚本不依赖 Node.js

2. 安装方式

推荐：官方脚本一行安装 —— 无需前置依赖，自动处理所有环境问题。

平台安装命令
macOS / Linux / WSL curl -fsSL https://claude.ai/install.sh | bash
Windows PowerShell irm https://claude.ai/install.ps1 | iex
Homebrew (macOS) brew install --cask claude-code
WinGet (Windows) winget install Anthropic.ClaudeCode

验证安装：

claude --version
# 输出示例: 2.1.81 (Claude Code)

npm 安装（不推荐）：npm install -g @anthropic-ai/claude-code —— 官方已不再推荐此方式，仅在特殊场景使用。国内网络慢时可临时切换镜像：--registry=https://registry.npmmirror.com

3. 更新与版本管理

claude update   # 手动更新（启动时也会自动检查更新）

可通过 settings.json 禁用自动更新：

{
  "env": { "DISABLE_AUTOUPDATER": "1" }
}

4. API 配置

Claude Code 支持多种 API 接入方式：

方式配置适用场景
Anthropic 官方 API 设置环境变量 ANTHROPIC_API_KEY=sk-ant-xxx 海外用户、稳定访问
OpenRouter / 兼容 Provider 设置 ANTHROPIC_BASE_URL + ANTHROPIC_AUTH_TOKEN 需要中转、国内网络
Claude 账号登录 启动后输入 /login 进行 OAuth 认证 Pro / Max / Teams / Enterprise 订阅用户

macOS / Linux 配置示例：

# 在 ~/.bashrc 或 ~/.zshrc 中添加
export ANTHROPIC_API_KEY="sk-ant-xxxxxxx"

Windows PowerShell 配置示例：

[Environment]::SetEnvironmentVariable("ANTHROPIC_API_KEY", "sk-ant-xxxxxxx", "User")

5. 首次登录与启动

  • 进入项目目录 cd /path/to/your/project
  • 启动 Claude Code claude —— 首次启动自动引导登录流程
  • 验证登录状态 输入 /login 可查看或切换账号
  • 开始第一次对话 直接用自然语言提问，Claude 自动读取项目上下文

    • 6. 第一次对话推荐

    启动后试试这些入门提示词：

    这个项目是做什么的？
这个项目用了哪些技术栈？
主入口文件在哪里？
帮我解释一下目录结构
你能做什么？

    核心体验：Claude Code 像一位有经验的同事——用自然语言描述需求，它会自动找到最佳实现方式。无需手动复制粘贴文件内容，它会自动读取所需上下文。

    7. 常用命令速查

    命令功能示例
    claude启动交互模式直接输入进入对话
    claude "任务描述"执行一次性任务claude "fix the build error"
    claude -p "查询"单次查询后退出（适合脚本）claude -p "what does git status do?"
    claude -c继续最近一次对话快速恢复上次会话
    claude -r从历史恢复对话选择要恢复的会话
    claude commit自动生成 Git commit 并提交分析变更 → 生成 message → 提交
    /help查看所有可用命令交互模式内使用
    /clear清除对话历史开始新话题
    /resume恢复之前中断的对话意外退出后恢复
    /config查看和修改配置交互模式内调整设置

    8. 用自然语言操作 Git

    Claude Code 内置 Git 感知能力，你可以用自然语言管理版本：

    我改了哪些文件？                            # → git status
提交我的修改，写上清晰的提交信息               # → git add + git commit
建一个叫 feature/xxx 的分支                   # → git checkout -b
帮我解决合并冲突                              # → merge conflict resolution
显示最近 5 次提交                             # → git log

    安装方式卸载命令

    🚨 新人首日必做 5 步（装完就用的正确姿势）

    来源：装完 Claude Code 就用？这 5 步没做等于白装 (HiddenState) · 原文链接 ↗

    ⚠️ 别上来就折腾 MCP、Hooks、子代理。新人第一天最重要的不是那些高级玩法，而是先把最基础的 5 步走对。顺序对了，它会越来越像同事——顺序错了，它就只是一个很贵的聊天框。

    新人装完最常见的问题：不知道干嘛，发个 hi，把它用成更贵的聊天框。然后提问题、等回复——看起来很顺，但真让它碰项目时就开始翻车：不懂项目背景，改代码跑偏，对话越聊越乱。

    1. 先跑一次 /init，把 CLAUDE.md 建起来 把技术栈、代码规范、目录结构、禁止操作写进去。比如「这是 React + TypeScript 项目」「不要随便改 package.json」「先给方案再动手」。
      核心理念：Claude Code 不是猜你心思的——它更像新同事，先交接，再干活。你写得越清楚，后面返工越少。
    2. 先在真实项目目录里启动，别在空白终端里瞎聊 Claude Code 最强的地方不是陪你聊天，而是能读你的项目、理解文件之间的关系。
      实操：第一步不是问它「你能干什么」，而是先进到你正在做的项目目录，用 cd /path/to/project && claude 启动它。哪怕只是一个小 demo，也比在空目录里空聊强得多。
    3. 第一天先用 Plan Mode，别一上来就让它直接改 新手最容易踩的坑就是刚装好就想看它一把梭。建议正好相反：先让它分析问题、先说计划，再决定要不要动手。
      好处：你很快就能判断它有没有理解对你的需求，也能避免它热情很高、方向却跑偏。
    4. 第一件事，先给它一个小任务 别上来就说「帮我重构整个项目」「把这个产品从零做出来」。第一天最适合的是这种小任务：
      帮我读一下这个项目结构
解释这个报错是怎么来的
告诉我这个函数为什么这么写
      用这种小任务磨合，你会更快知道它适不适合你的工作方式，也更容易建立信任感。
    5. 聊乱了就 /compact，任务结束就 /clear 用了好几轮之后觉得 Claude Code "不稳定"，问题往往不是模型突然变笨了，而是上下文已经聊脏了。
      一个好习惯：一个任务聊太久，信息会越来越杂 → 用 /compact 把前面内容压成重点；一个任务做完 → 用 /clear，别带着上一轮的上下文去做下一件事。

    把上面这 5 步走完，你会明显感觉到：它不是一个更会写代码的聊天框，而是一个可以慢慢合作起来的搭档。

    一 目录结构全景

    来源：Claude Code 目录结构解析 + Anthropic 官方文档 · 原文链接 ↗

    Claude Code 的配置体系分为项目级（<project>/.claude/）和用户级（~/.claude/）两个层级。理解这个目录结构是搭建 Harness 的基础。

    项目级目录树

    项目级配置可提交 Git 共享给团队，本地文件（.local.*）自动 gitignored。

    <project>/
├── CLAUDE.md                          # 🔵 项目记忆（共享给团队）
├── CLAUDE.local.md                    # 🟢 项目记忆（本地，不提交 Git）
├── .mcp.json                          # 🔵 项目级 MCP 服务器配置（共享）
└── .claude/
    ├── settings.json                  # 🔵 项目共享设置
    ├── settings.local.json            # 🟢 项目本地设置（gitignored）
    ├── commands/                      # 自定义斜杠命令
    │   └── *.md                       #   每个文件 → /project:xxx
    ├── rules/                         # 模块化规则（按需加载）
    │   ├── *.md                       #   通用规则（始终加载）
    │   └── path-spec/*.md             #   路径限定规则
    ├── hooks/                         # Hook 脚本存放
    │   └── *.sh / *.py / *.js
    ├── skills/                        # 项目级 Skills
    └── agents/                        # 项目级自定义 Agent

    用户级目录树（~/.claude/）

    ~/.claude/
├── settings.json                      # 全局设置（权限、hooks、MCP）
├── settings.local.json                # 全局本地覆盖设置（优先级最高）
├── credentials.json                   # 认证凭据（自动生成，勿手动编辑）
├── .claudesignature                   # 内部签名（自动管理）
├── commands/                          # 全局自定义命令 → /user:xxx
│   └── *.md
├── rules/                             # 全局规则
│   └── *.md
├── skills/                            # 全局 Skills
├── agents/                            # 全局自定义 Agent
├── projects/                          # 项目级个人记忆存储
│   └── <path-hash>/
│       └── CLAUDE.md                  # 对特定项目的个人私有记忆
├── cache/                             # 缓存（可安全删除，自动重建）
├── ide/                               # IDE 集成数据
├── statsig/                           # 功能标志/实验配置
└── tempo/                             # 会话临时数据

    补充：~/.claude.json（用户主目录下）存储 local/user scope 的 MCP 服务器配置。

    核心文件/目录逐项详解

    文件/目录级别共享用途与说明
    CLAUDE.md 项目✅ Git 项目"大脑"。存放项目约定、架构说明、编码规范、技术栈信息。每次会话自动加载到 system prompt，贯穿整个对话。回报率最高的文件，砍到 20 行效果最好。
    CLAUDE.local.md 项目❌ 本地 个人项目偏好。本地数据库地址、个人调试习惯等，不影响团队其他人。与 CLAUDE.md 叠加生效。
    settings.json 项目✅ Git 项目级配置：权限规则（allow/deny）、hooks 声明、MCP 服务器等。团队统一配置。
    settings.local.json 项目❌ 本地 个人覆盖设置，可覆盖 settings.json，只影响自己。
    commands/*.md 项目/用户可选 自定义斜杠命令。文件名即命令名。项目级触发 /project:xxx，用户级 /user:xxx。支持 $ARGUMENTS 变量传参。
    rules/*.md 项目/用户可选 模块化规则，按需加载。支持路径限定匹配——文件名即匹配规则（如 frontend/**.tsx.md 仅在 frontend 下的 tsx 文件激活）。无路径限定符的文件始终加载。
    hooks/ 项目可选 Hook 脚本存放目录。Hook 在 settings.json 中声明，脚本放这里。支持 25 种事件（SessionStart、PreToolUse、PostToolUse、Stop 等），4 种 Hook 类型（command/http/prompt/agent）。
    skills/ 项目/用户可选 可复用技能模块。每个 Skill 是独立目录，包含 SKILL.md（指令 + 元数据）和可选的 scripts/、references/、assets/。延迟加载，按需激活。
    agents/ 项目/用户可选 自定义 Agent 配置。可指定特定系统提示词、模型、工具权限，用于特定场景的子智能体。
    .mcp.json 项目✅ Git 项目级 MCP 服务器配置。定义外部工具集成（数据库、API、GitHub 等）。
    credentials.json 用户❌ 认证凭据。⚠️ 自动生成，不要手动编辑，不要提交到版本控制。

    设置文件优先级（从高到低）

    优先级设置来源说明
    1（最高）Managed Policy Settings企业管理员配置
    2~/.claude/settings.local.json全局本地覆盖
    3~/.claude/settings.json全局设置
    4.claude/settings.local.json项目本地覆盖
    5（最低）.claude/settings.json项目共享设置

    Hook 支持的全部 25 种事件

    🟢 会话生命周期

    SessionStart, SessionEnd, Stop, StopFailure, InstructionsLoaded, ConfigChange, PreCompact, PostCompact

    🟡 用户交互

    UserPromptSubmit, PermissionRequest, PermissionDenied, Notification, Elicitation, ElicitationResult

    🔵 工具调用

    PreToolUse, PostToolUse, PostToolUseFailure

    🟣 Agent / 团队

    SubagentStart, SubagentStop, TeammateIdle, TaskCreated, TaskCompleted

    🟠 文件 / 目录

    FileChanged, CwdChanged, WorktreeCreate, WorktreeRemove

    ⚠️ 社区惯例 vs 官方支持

    以下文件名在社区中常见，但 Claude Code 不会自动识别和加载——如需使用必须在 CLAUDE.md 中显式引用：

    社区惯例文件社区用途官方替代方案
    .claude/context.md额外上下文在 CLAUDE.md 中手动引用
    .claude/instructions.md额外指令在 CLAUDE.md 中手动引用
    .claude/conventions.md编码约定在 CLAUDE.md 中手动引用
    .claude/memory.md记忆文件官方已用 CLAUDE.md + CLAUDE.local.md 替代
    .claude/permissions.json权限配置官方已合并到 settings.json
    .claude/prompts/提示词模板官方用 commands/ 替代
    .claude/workflows/工作流官方用 hooks + commands 替代

    二 Anthropic 工程师的四条黄金法则

    来源：Anthropic 工程师用 Claude Code 的四条黄金法则 · 原文链接 ↗

    法则一：Prompt Skills，不是 Prompt Claude

    不要每次都写新 prompt。把重复性工作封装成 Skill。以后不再写 custom prompts，而是调用已有的 skills。就像你不会每次发微信都重写程序，而是直接打开微信 App 一样。

    实操：让 Claude 分析你过去一周的工作内容，找出有哪些重复性事务可以封装成 Skill。

    法则二：Skills 不只是 Prompt——三层结构

    层级名称作用关键细节
    Layer 1描述Claude 判断是否启用此 skill 的依据不需要显式调用，Claude 自动判断
    Layer 2指令操作手册一步步指导：先做什么、后做什么
    Layer 3工具真正的杠杆所在脚本、API、参考文件等

    核心洞察：大多数人停在 Layer 2（写很精美的 prompt），但 Anthropic 工程师把精力放在 Layer 3（工具层）。如果能用代码，就别用 AI——让 AI 帮你写一次，然后无限复用。

    法则三：构建可组合的 Skills，而不是定制的 Skills

    多个小型、专注、可复用的 skill，而不是一个巨大的"万能" skill。拆分的三个理由：

    • 问题容易定位——小 skill 出错一眼看到，巨无霸找 bug 找到崩溃
    • 改进可以积累——更新专注的 skill，所有用到它的 workflow 自动升级
    • 复用代替重建——写了「检查域名」的 skill，插到任何 workflow 里直接用

    两个关键技术模式：

    模式核心思路原理
    把脚本保存到 SkillAI 帮我写一次代码，以后直接运行脚本代码是确定性，AI 是概率性。用代码替代 token → 更便宜、更快、更可重复
    控制 Skill 调用权限user_invocable=false 隐藏；disable_model_invocation=true 需手动高风险操作（部署、发消息）设为手动触发，AI 不能自动调用

    法则四：Skills 每次使用都在变聪明

    进化闭环：运行 skill → 评估输出发现不足 → 更新 skill → 循环。每次运行后问自己：这是一次性修复，还是应该永久写进 Skill？如果是永久的 → 更新 skill（加规则、加例子、加边界处理）。

    运行 Skill
    →
    评估发现不足
    →
    永久更新 Skill
    →
    下次更好用
    ↻

    三 五步搭建 Claude Code Harness

    来源：花一小时搭好 Claude Code Harness，AI 写代码质量立竿见影 · 原文链接 ↗

    约15分钟，5步实操，每步3分钟，不要跳步按顺序来。使用真实项目目录，不要新建 demo 项目。

    1. 第一步：把 CLAUDE.md 写对（回报率最高的 5 分钟） 规则放 CLAUDE.md，工作流放 Skills。只写"AI 需要在你开口之前就知道的事"。
      踩坑提醒：别当项目文档写。砍到 20 行，效果比 300 行好得多。 
      # 项目概要
技术栈：Next.js 15 + tRPC + PostgreSQL
跑测试：pnpm test

# 全局约定
- 金额相关计算一律用"分"，禁止浮点数
- 组件文件用 named export，不用 default export
    2. 第二步：配一个 Hook，别每次都从头自我介绍 SessionStart Hook 自动注入 git 状态、当前分支、最近提交日志。让 Claude 一上来就知道项目长什么样、你正在做什么。 
      {
  "hooks": {
    "SessionStart": [{
      "type": "command",
      "command": "node .claude/hooks/session-context.mjs"
    }]
  }
}

    12 课递进式构建，从 20 行 Python 循环到多 Agent 自治系统

    Phase 1 · 让它跑起来

    S01 — Agent Loop：用 20 行 Python 造出你的第一个 AI Agent

    核心概念：One loop & Bash is all you need — 一个 while True 循环 + 一个 Bash 工具 = 一个能操作真实世界的 Agent。

    维度内容
    解决的问题一切 Agent 的最小骨架——让智能体能运转起来
    实现方式while True → 调模型 → 检查 stop_reason → 如果是 tool_use 则执行工具并将结果喂回，否则停止
    关键代码
    while True:
    response = client.messages.create(model=MODEL, messages=messages, tools=TOOLS)
    if response.stop_reason != "tool_use": return
    # 执行工具，追加结果到 messages，继续循环
    设计决策模型自己决定何时停止——不需要你写任何判断逻辑。实测中模型能自主纠错（Linux 命令失败后自动换 Windows 命令）
    标签20行代码ReAct Loop自主决策

    S02 — Tool Use：给 Agent 加工具——Dispatch Map 模式详解

    核心概念：加一个工具，只加一个 handler。通过 dispatch map（分发映射）将工具名映射到处理函数，实现工具扩展与循环逻辑的完全解耦。

    维度内容
    解决的问题只有 Bash 什么都能干太危险——需要"能用什么、不能碰什么"的围栏
    实现方式定义工具描述（给模型看）+ 对应的 handler 函数（执行时用），通过 dispatch map 桥接两者
    设计决策新增工具只需注册到 dispatch map，循环代码碰都不用碰。O(1) 查找、显式声明、不碰主循环
    标签dispatch map工具围栏解耦

    Phase 2 · 让它干得好

    S03 — TodoWrite：让 Agent 先想后做——规划系统

    核心概念：没有计划的 Agent 走哪算哪——给它一个 TodoManager，先列步骤再动手。

    维度内容
    解决的问题Agent 缺乏规划能力，执行混乱、容易跑偏
    实现方式在循环里加入 Nag Reminder（催促提醒）机制——连续 3 轮没更新 Todo 列表就自动生成提醒文本注入下轮 prompt
    设计决策通过 nag reminder 而非修改 system prompt 来强制 Agent 遵循计划——完成率直接翻倍
    标签规划先行Nag Reminder不跑偏

    S04 — Subagent：拆解大任务——上下文隔离

    核心概念：大任务拆小，每个小任务用干净的 messages[]——子 Agent 的对话历史与主 Agent 完全隔离，只返回结果摘要。

    维度内容
    解决的问题大任务执行时上下文污染——子任务的结果、中间推理、工具输出混杂在一条对话里越来越乱
    实现方式主 Agent 把大任务拆分，每个子任务创建独立的 messages[] 数组，在干净上下文中执行完毕后只汇报结果摘要给主 Agent
    设计决策完全隔离——子 Agent 看不到主 Agent 的对话历史，主 Agent 也看不到子 Agent 的中间过程。这对保护主会话上下文窗口至关重要
    标签上下文隔离子Agent只收摘要

    S05 — Skills：按需加载领域知识——Skill 机制

    核心概念：用到什么知识，临时加载什么知识——通过 tool_result 按需注入领域知识，而非预先塞进 system prompt。

    维度内容
    解决的问题system prompt 塞太多知识 → token 浪费 + 注意力稀释 + 模型抓不住重点
    实现方式领域知识以 Markdown 文件（如 SKILL.md）形式存储。启动时只给"菜单"（skill 的描述列表），模型判断需要哪个 skill 时通过 tool_result 加载完整"食谱"
    设计决策这就是 Claude Code 的 Skill 加载机制的底层原理——懒加载而非预加载，按需注入。可以写 50 个 Skill，但只为一个 Skill 的正文付费
    标签懒加载SKILL.md按需注入

    S06 — Context Compact：无限对话——上下文压缩三层策略

    核心概念：上下文总会满，要有办法腾地方——从最便宜到最贵分层处理。

    维度内容
    解决的问题长对话中上下文窗口被撑满，Agent 无法继续工作
    实现方式三层漏斗式压缩：Layer 1（最便宜）— 丢弃冗余的工具输出结果；Layer 2（中间）— 超出阈值时自动摘要历史对话；Layer 3（最贵但最后手段）— Agent 可主动发起 compact 压缩整个上下文
    设计决策从便宜到昂贵分层处理，而非简单截断。生产环境踩出的教训：MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3 次连续压缩失败后熔断
    标签三层压缩无限对话漏斗策略

    Phase 3 · 让它记得住

    S07 — Task System：任务持久化——文件级 DAG 任务图

    核心概念：大目标拆成小任务，排好序，记在磁盘上——从内存清单升级为持久化到磁盘的任务图（DAG），关机了任务还在。

    维度内容
    解决的问题任务只在内存 → 进程退出即丢失；任务间依赖无法管理
    实现方式每个任务一个 JSON 文件，含状态（pending/in_progress/completed）和依赖关系（blocks/blockedBy）。DAG 回答三个问题：什么可以做？什么被卡住？什么做完了？
    设计决策选择文件级持久化而非数据库——简单可靠，天然适合版本控制。这个任务图是后续 S08-S12 全部机制的协调骨架
    标签文件持久化DAG依赖管理

    S08 — Background Tasks：后台执行——异步任务与通知队列

    核心概念：慢操作丢后台，Agent 继续想下一步——Fire-and-Forget 模式。

    维度内容
    解决的问题Agent 执行耗时操作（构建、测试）时被阻塞，无法继续思考和规划
    实现方式后台 daemon threads（守护线程）跑耗时命令，完成后通过 notify queue（通知队列）将结果自动注入回 Agent 的上下文
    设计决策Agent 不用干等结果——等待期间可继续规划和执行其他任务。通知队列作为后台与前台 Agent 的解耦通信桥梁
    标签Fire-and-Forget守护线程异步通知

    Phase 4 · 让它带团队

    S09 — Agent Teams：多 Agent 协作——团队与邮箱系统

    核心概念：任务太大一个人干不完，要能分给队友——持久化的队友 + 异步 JSONL 邮箱。

    维度内容
    解决的问题单 Agent 能力上限——一个人忙不过来，需要多 Agent 分工协作
    实现方式领导 Agent 创建队友 → 队友信息持久化存储 → 通过 JSONL 邮箱异步通信。每条消息追加写入 JSONL 文件，天然适合异步消息队列
    设计决策选择 JSONL 格式作为邮箱消息格式（追加写入，不需要解析完整文件）。邮箱机制实现了解耦的异步协作——Agent 不需要同时在线
    标签多AgentJSONL邮箱异步通信

    S10 — Team Protocols：团队协议——状态机驱动的协商

    核心概念：队友之间要有统一的沟通规矩——request-response 模式驱动所有协商。

    维度内容
    解决的问题多 Agent 之间缺乏统一沟通规范 → 协作混乱、消息丢失、状态不一致
    实现方式定义三类协议：关机协议（Agent 安全关闭的握手流程）、计划审批 FSM（有限状态机管理计划审批）、request-response 统一模式（所有协商都带唯一 ID）
    设计决策用状态机而非自由文本协商——确保协作行为的可预测性和可靠性。统一"请求-响应 + 唯一 ID"模式避免消息乱序
    标签FSM状态机关机协议request-response

    S11 — Autonomous Agents：自治 Agent——自组织任务认领

    核心概念：队友自己看看板，有活就认领——从"被动接受指令"到"主动认领任务"的范式转变。

    维度内容
    解决的问题S09-S10 仍需主 Agent 逐个分配任务——存在单点瓶颈，领导 Agent 成为调度瓶颈
    实现方式Agent 在 idle cycle（空闲周期）中自动扫描任务板（基于 S07 的 DAG 任务图），找到可做任务（依赖已满足 + 无人认领）就自动认领执行
    设计决策每 5 秒轮询看板 → 找活干 → 60 秒无任务自动关机。实现了真正的自组织，去中心化调度
    标签自组织自动认领去中心化

    S12 — Worktree Isolation：终极隔离——Worktree 并行执行

    核心概念：各干各的目录，互不干扰——每个任务绑定一个独立的 git worktree 目录。任务管目标，worktree 管目录，按 ID 绑定。控制面与执行面彻底分离。

    维度内容
    解决的问题到 S11 为止所有任务共享一个目录——两个 Agent 同时改同一个文件就互相污染，并行执行名存实亡
    实现方式每个任务 → 独立 git worktree 目录 → 独立分支开发 → 完成后 merge 回主干。利用 git 原生机制而非自己造轮子
    设计决策通过任务 ID 与 worktree 路径的绑定关系，实现并行执行时的文件系统级隔离。这是 12 课的终极形态——多个自治 Agent，各自持有独立 worktree，通过任务图和邮箱协作
    标签Worktree隔离文件级隔离并行执行
