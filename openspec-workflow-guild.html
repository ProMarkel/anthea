OpenSpec · Propose Phase

游戏需求提案工作流

一套轻量级、叙事驱动的产品需求规格框架，让团队的每一次决策都有据可查、可追溯、可复盘。

模拟经营手游Cocos CreatorGo 后端15+ 人团队

为什么需要 OpenSpec？

软件项目持续产生大量决策——做什么、为什么、怎么做。没有一致的记录方式，上下文就会散落在 Slack 聊天、PR 描述和半遗忘的会议中。OpenSpec 让规格流程变得刻意、可审阅、可版本化。

原则 1

叙事优于表单

提案、规格、决策以可读文档形式存在。无论是人还是 LLM，都无需交叉引用工单系统就能理解设计依据。

原则 2

变更即仪式

每一次有意义的变更都经历：提案 → 审阅 → 批准 → 实施 → 关闭。跳过任何阶段本身就是一次值得记录的决定。

原则 3

不做 BPMN

流程应该简单到一张作弊小抄就能装下。过度工程化流程本身，恰恰违背了流程的初衷。

原则 4

人人可提案，非人人可决策

提案者和最终审批者分离，保持提案的诚实性和决策的连贯性。

原则 5

意图版本化

规格文档一旦批准即冻结。增补内容以追加方式记录，从不编辑历史文本，确保设计意图的完整溯源。

用户身份与权限

hyl-propose 在每次触发时自动读取 CLAUDE.local.md 获取当前用户身份，用于角色判定和权限控制。PO（提案负责人）是流程中的临时角色——发起提案并撰写 story.md 的策划自动成为该提案的 PO。

CLAUDE.local.md — 本地身份文件

每个团队成员的本地身份配置极其简单，只需一行姓名和一行角色：

# 本地用户身份配置 **姓名**：张三（昵称：小张） **角色**：系统策划 > PO（提案负责人）是提案流程中的临时角色，发起提案并撰写 story.md 的人自动成为该提案的 PO。制作人或主策划可指定更换。
模板文件：CLAUDE.local.template.md 可供团队成员复制并填写。如果首次使用 hyl-propose 时尚未创建此文件，AI 会自动引导你完成身份配置。

身份引导流程

当 CLAUDE.local.md 不存在或无法读取时，AI 不会继续任何流程，而是先引导用户完成身份配置：

步骤 1：询问姓名

AI："未检测到你的本地身份配置。在继续之前，请先告诉我——你的姓名（全名）和常用昵称是什么？"

步骤 2：选择角色

AI 列出 9 种角色选项：制作人、主策划、系统策划、数值策划、文案策划、交互设计师、主程序、开发程序、QA。

步骤 3：保存配置

AI 将信息写入 CLAUDE.local.md，提示："身份信息已保存到 CLAUDE.local.md，之后可以直接使用。"

步骤 4：继续流程

身份配置完成后，AI 自动回到原来的流程（新建 / 续接 / 检查模式），后续每次触发均自动识别。

角色分类与权限

类别包含角色propose 阶段权限

PO 更换规则

PO 是提案流程中的临时角色，可在以下情况下更换：

制作人指定更换

制作人在审阅 story 或后续步骤时，可指定新的 PO。更新 proposal-index.md 的 PO 字段和 story 执行人列。

主策划指定更换

主策划在审阅过程中，可提议更换 PO，经制作人确认后生效。写入状态变更记录。

当 PO 与主策划在审阅中意见不一致时：协商 → 协商不成 → 制作人介入裁决（制作人拥有最终裁决权）。

步骤详情

每个步骤聚焦单一职责，依赖前置产物的审阅通过状态。

步骤 1 · 需求创建

产物：story.md · 执行人：PO · 审阅人：制作人

从特定玩家角度出发，描述行为目标和价值。使用「作为…（角色），我想要…（目标），以便…（价值）」句式。审阅通过后 PO 正式成为该提案的 Proposal Owner。

步骤 2 · 规则设计

产物：mechanics.md · 执行人：系统/主策 · 审阅人：PO + 主策

基于 story 进行核心机制和逻辑规则设计。包含状态机/流程图、规则逻辑详述、边界条件、异常路径、与现有系统交互点。

步骤 3 · 数值设计

产物：params.md · 执行人：数值策划 · 审阅人：PO + 主策

基于 mechanics 进行配置表结构、常量参数、数值阈值、运算公式设计，并生成覆盖正常/边界/异常的开发调试数据。

步骤 4 · 包装设计

产物：theme.md · 执行人：文案策划 · 审阅人：PO + 主策

基于 mechanics 和 params，结合游戏世界观，进行功能名称、道具描述、UI 文本、视觉方向的全面设计。

步骤 5 · 交互设计

产物：ux.md · 执行人：交互设计师 · 审阅人：PO + 主策

基于 mechanics 和 theme，进行界面层级、信息架构、交互流程、状态覆盖、分辨率适配的设计。

修订规则

审阅通过后产物不可修改——任何修订必须创建 -fixNN 版本，走正式修订流程。

两种修订场景

场景 A：审阅通过前 · 打回

当前步骤被审阅人打回 → 执行人直接修改原文件，重新提交审阅。不创建 -fix 版本。

场景 B：审阅通过后 · 修订

后续步骤发现前置产物需修订 → 创建 -fixNN 版本，原文件保留不动。修订后从问题步骤重启，按序重走后续步骤。

级联规则

修订发起后，后续步骤是否需要创建 -fix 版本，取决于该步骤的当前状态：

已审阅通过

必须创建 -fix 版本——已锁定的产物不可修改

未提交审阅（撰写中/待审阅）

直接在原稿内修改，不创建 -fix 版本

修订状态流转

story.md → [审阅通过] → mechanics.md → [审阅通过] → params.md → [审阅通过] → ux.md（撰写中，发现 mechanics 需修订） → 创建 mechanics-fix01.md → [审阅通过] → params.md 已审阅通过 → 创建 params-fix01.md（级联修订）→ [审阅通过] → ux.md 未提交审阅 → 在原稿内直接修订 → [审阅通过] → 制作人最终审核 → [通过] → propose 完成

产物状态变更

阶段原产物状态操作
修订发起已通过 → 修订中在修订备注中写明发起环节、原因、版本、修订人、审阅人
fix 版本创建—在修订备注中声明：修订版本、基于版本、发起环节、原因
fix 审阅通过修订中 → 已修订更新「当前有效版本」指向 fix 版本

proposal-index.md 铁律

proposal-index.md 贯穿整个 propose 阶段，是提案的「中枢神经系统」。每次状态流转必须即时更新，不得延迟或遗漏。

铁律：状态变更和 proposal-index 更新是原子操作——先更新产物文件，再更新 proposal-index，两者必须在同一次操作中完成，不可拆分。

多人协作接力

本流程涉及 7 种角色在 5 个步骤间接力。proposal-index.md 是唯一状态机，Git 是同步中枢，hyl-propose 是执行引擎。

接力总则

执行人完成 → 更新产物 + proposal-index → git commit & push → 通知下一人 下一人 git pull → 打开 proposal-index 确认状态 → 用 hyl-propose 续接

hyl-propose 三种模式

新建模式

输入"发起提案 功能名"或"新建提案 功能名"。仅限策划类角色（制作人/主策划/系统策划/数值策划/文案策划/交互设计师）。发起提案的策划自动成为该提案的 PO。

续接模式

输入"继续提案 功能名"。AI 读取 proposal-index.md 识别当前状态，进行三级身份匹配（完全匹配 / 角色匹配 / 跨角色匹配），确认后引导进入对应步骤。

检查模式

输入"检查 功能名 的进度"。所有角色均可使用。AI 展示各步骤状态，进行中的步骤高亮执行人，主动提示可接续的步骤。

执行人列 — 身份验证

proposal-index.md 的产物状态表中包含「执行人」列，AI 在续接时通过 CLAUDE.local.md 获取当前用户身份，进行三级匹配：

通知模板

Git 提交本身不主动通知。实际使用时，提交人通过团队即时通讯工具（Slack / 企业微信等）通知下一个人，附上提案名称和 proposal-index.md 链接：

@张三 daily-checkin 的 story 已审阅通过，轮到你写 mechanics 了。proposal-index 已更新，pull 后用 /hyl-propose 继续。

接棒人操作

1. git pull

获取最新代码，确保 proposal-index.md 和产物文件是最新状态。

2. 确认状态

查看 specs/in-progress/<日期>-<功能名>/proposal-index.md 确认当前状态和待办事项。

3. 输入续接指令

在对话中输入"继续提案 功能名"，AI 自动识别当前提案并进入续接模式。

4. 确认身份

AI 根据 proposal-index 中的执行人列确认当前用户身份，确认后引导进入对应步骤。

产物文档结构

所有产物文档统一按以下顺序组织，基础信息字段直接以 **key**：value 格式换行，无需标题项。

# 标题 **功能 ID**：`模块-功能名` **创建时间**：YYYY-MM-DD **更新时间**：YYYY-MM-DD **提案负责人（PO）**：@name **执行人**：@name（角色） **前置依赖**：mechanics.md（审阅通过） **状态**：撰写中 | 待审阅 | 已通过 | 已打回 | 修订中 | 已修订 **当前有效版本**：— > **修订备注**：无 --- ## 版本历史 ... ## 审阅记录 ... ## 正文...

快速开始

使用 hyl-propose 技能，在对话中一句话即可发起提案。首次使用前请先配置本地身份。

首次使用：身份配置

0. 配置身份

复制 CLAUDE.local.template.md 为 CLAUDE.local.md，填写姓名和角色。如果跳过此步，首次触发 hyl-propose 时 AI 会自动引导你完成身份配置。

1. 发起提案

在对话中告诉 AI："发起提案 功能名"（格式：模块-功能名，如 shop-daily-checkin）。仅限策划类角色，AI 自动创建提案目录和初始文件，引导进入 story 撰写。发起提案的策划自动成为该提案的 PO。

2. 续接提案

当上一个步骤完成后，pull 代码后输入 "继续提案 功能名"。AI 自动读取 CLAUDE.local.md 识别身份，进行三级匹配（完全匹配 / 角色匹配 / 跨角色匹配），确认后引导进入对应步骤。

3. 检查进度

随时输入 "检查 功能名 的进度"。所有角色可用。AI 展示各步骤状态，若你是进行中步骤的执行人，会高亮提示"是否继续完成？"。

4. 接力提交流程

完成当前步骤后：更新产物文件 + proposal-index.md → git commit & push → 通过 IM 通知下一个人。下一个人 git pull 后用续接模式继续。

5. 最终审核

5 步全部通过后，制作人最终审核 → 通知主程序、开发程序、测试 → 提案进入 design 阶段。

常见问题

Q: 我是程序/QA，能发起提案吗？
程序类角色无法直接新建提案。如有功能优化建议，可转达策划团队（制作人/主策划/系统策划/数值策划/文案策划/交互设计师）评估后发起提案。你可以在检查模式中查看提案进度。

Q: 审阅被打回了怎么办？
直接修改原文件，重新提交审阅。不需要创建 -fix 版本。

Q: 发现前面已通过的步骤需要改怎么办？
创建 -fixNN 版本，走修订流程。后续步骤根据自身状态（已审阅/未审阅）决定是否级联创建 -fix。

Q: PO 和主策划意见不一致怎么办？
先协商，协商不成由任意一方请求制作人介入裁决。制作人拥有最终裁决权。

Q: 技术团队什么时候介入？
propose 阶段全部完成后，通知主程序、开发程序、测试。他们在 design 和 tasks 阶段介入。
