一 CLAUDE.md 里加入「第一性原理」

来源：经验分享 · 原文链接 ↗

在 CLAUDE.md 中加入以下提示词，让 Claude Code 从"执行者"变成"思考伙伴"：

# 第一性原理思考
请使用第一性原理思考。你不能总是假设我非常清楚自己想要什么和该怎么得到。
请保持审慎，从原始需求和问题出发，如果动机和目标不清晰，停下来和我讨论。
如果目标清晰但是路径不是最短，告诉我，并且建议更好的办法。

效果：加入后，Claude Code 会主动质疑不清晰的需求，建议更短路径，而不是盲目执行。作者借此删掉了别人 vibe coding 产出的大量冗余代码。

一句话总结：让 AI 从"你说什么我做什么"变成"你说的我不确定，咱们先对齐"。

此技巧同样适用于 Codex.md、AGENTS.md、CODEBUDDY.md 等同类文件（各 AI 编码工具的项目规则文件）。

二 12 条"天条"让 Vibe Coding 错误率从 85% 降到 8%

来源：Ryan（AI炊事员Ryan）· GitHub ↗ · 原文链接 ↗

Karpathy 原始 4 条规则不够用——Agent 工作流引入了新的失败模式，扩展为 12 条。

编码阶段（原 Karpathy 4 条 + 扩展）

1Think Before Coding（编码前先思考）

编码前先说明假设和不确定性。防止：静默假设、误解需求。

⚠️ 防止：静默假设、需求误解

2Simplicity First（简单优先）

用最少代码解决问题。今天多写一行，明天多改十分钟。

⚠️ 防止：过度工程、臃肿抽象

3Surgical Changes（精准修改）

只改必须改的地方。改之前用 grep 确认影响范围。

⚠️ 防止：无关修改、误伤代码

4Goal-Driven Execution（目标驱动执行）

定义成功标准并循环验证。每次改动后回答：这个改动让我更接近目标吗？

⚠️ 防止："看起来完成了"的假象

Agent 执行阶段（新增 8 条）

5Use the Model Only for Judgment Calls（模型只做判断）

确定性逻辑交给代码，AI 只做判断。能写 if-else 就别让 AI 生成推理步骤。

⚠️ 防止：AI 替代 if-else、不必要的 token 消耗

6Token Budgets Are Not Advisory（Token 预算不是建议）

单任务 4k / 单 session 30k token 上限。超预算 = 质量悬崖。

⚠️ 防止：长 session 漂移、质量衰减

7Surface Conflicts, Do Not Average Them（暴露冲突，不要和稀泥）

遇到冲突模式显式选择，不和稀泥。让 AI 列出冲突点并给出建议。

⚠️ 防止：代码风格混乱、逻辑不一致

8Read Before You Write（先读后写）

写代码前先读现有上下文。目录结构、命名约定、依赖关系——先理解再动手。

⚠️ 防止：重复实现、误判架构

9Tests Verify Intent, Not Just Behavior（测试验证意图，不止行为）

测试要说明"为什么这样写"，不只是"它通过了"。好测试 = 可执行的需求文档。

⚠️ 防止：浅层测试、无意义通过

10Checkpoint After Every Significant Step（每步后做检查点）

每步后做状态总结，写在 CLAUDE.md 或 session log。多步骤任务必须序列化思考。

⚠️ 防止：多步骤漂移

11Match Codebase Conventions（遵守代码库约定）

遵守现有约定，即使你不同意。一致性 > 个人喜好。先读懂项目的"方言"，再开口说话。

⚠️ 防止：风格分叉

12Fail Loud（不确定就大声说）

不确定就大声说，不许静默跳过。三种处理方式：问用户 / 中止 / 标记 TODO。

⚠️ 防止：假成功、静默失败

关键数据：加规则前 85% 轮次撞坑 → 加规则后降至 8%

使用方式：CLAUDE.md / Cursor 规则 / Skill 三种格式均已准备好（GitHub ↗）

三 一份 AGENTS.md 让代码规范率从 60% 飙升到 95%

来源：天外飞星吆（Java进步）· 原文链接 ↗

AGENTS.md（部分工具叫 CLAUDE.md）是给 AI 的"项目说明书"，放在项目根目录，AI 自动读取，永久生效。

模板核心板块

板块关键内容
项目概述技术栈、SDK 版本、目标用户、项目背景
编码规范命名规则（变量/函数/类）、代码格式、注释规范、禁止操作
架构约束分层规则、依赖方向、技术选型说明、数据流向
测试要求覆盖率目标、测试框架、Mock 策略
提交规范分支命名、Commit 格式（Conventional Commits）、PR 模板
常见术语业务术语字典（AI 不懂你的业务黑话）
性能约束启动时间、内存上限、API 超时、并发限制

进阶技巧

① 添加负面示例

告诉 AI 不要做什么（比正面规则更有效）。例："禁止在渲染循环中创建新对象""禁止直接操作 DOM"

② 添加常见错误和修复

AI 能自动避免重复踩坑。例："之前在 XX 场景下误用了 YY，正确做法是 ZZ"

③ 版本控制

记录规范变更历史，AI 能理解"为什么现在是这样的"。在 AGENTS.md 末尾加变更日志。

④ 多项目共享

用 Git Submodule 复用通用规范。团队统一 AGENTS.md 基础版 + 各项目叠加定制版。

建议长度

类型长度适用场景
基础规范500-1000 字小项目、个人项目
详细规范2000-3000 字中型项目、团队协作
拆分规范超过 5000 字建议拆分大项目、多模块

⚠️ 重要：AGENTS.md 不是项目说明文档！它是"给 AI 的操作手册"，不是"给人类的项目介绍"。不要把 README 的内容原样搬进来。

四 三篇文章的关系：AI 编码规范实践链

这三篇文章形成了一条清晰的 AI 编码规范实践链，从思维框架到行为规则到项目配置：

层次文章核心解决什么问题
思维层第一性原理（文章1）让 AI 学会质疑需求AI 盲目执行、不思考
行为层12 条天条（文章2）告诉 AI 什么不能做Agent 工作流的失败模式
配置层AGENTS.md 规范（文章3）告诉 AI 你的项目怎么做AI 不懂项目上下文

实践建议：先加第一性原理（5 分钟）→ 再写 AGENTS.md 基础版（15 分钟）→ 最后加 12 条天条（30 分钟）。顺序对了，AI 会越来越像同事。
