01 人员结构 & 职责 策划组构成 · 岗位职责定义
1.1 策划人员结构1.1
主策划（制作人兼任）
系统策划（1 主 1 辅）
交互策划
数值策划
内容策划（文案策划）

📌 制作人兼任主策划时，部分职能由主系统策划分担。
👑
1.2.1 主策划（or 执行主策划）
  • 协助制作人，确定项目整体设计方向
  • 协助制作人，确定项目整体系统框架设计
  • 协同数值策划，确定项目整体数值结构设计
  • 负责项目核心系统设计，及 Demo 版本内容规划
  • 制定并控制策划团队工作计划及分工，确保按进度实施
  • 指导、跟踪整体设计效果，确保各具体方案与整体设计理念吻合
  • 协调策划团队与其他研发业务组的资源配合，保证项目整体进度
⚙️
1.2.2 系统策划
  • 配合主策划，参与项目整体系统框架设计
  • 协助主策划，确定项目核心系统设计方向
  • 负责项目主要系统的设计，并制作完整开发需求
  • 负责跟进项目需求的开发制作，保证需求实现进度
  • 负责需求验收及测试用例审核，保证实现准确性及体验标准
🖱️
1.2.3 交互策划
  • 配合主策划，制定项目界面交互设计规范
  • 协助具体系统策划，负责各系统的交互界面原型及动特效设计
  • 负责整理制作界面设计制作需求，协调跟进 UI 美术制作输出 UI 素材
  • 负责验收反馈界面相关需求实现结果，并协调美术 & 程序团队优化改进
🔢
1.2.4 数值策划
  • 配合主策划，负责项目整体数值结构设计及优化
  • 协同具体系统策划，负责各系统的具体数值设计及优化
  • 负责项目所有配置结构的制定、更新、维护，以及数值专项文档的撰写、维护
  • 负责项目经济体系的搭建、优化、完善，以及平衡性调整
  • 协助运营，完成运营相关数值工作
📖
1.2.5 内容策划（文案策划）
  • 配合制作人及主策划，确定项目世界观方向设定
  • 负责项目世界观具体元素设定，并制作基础设定文档
  • 负责项目各系统功能的包装设定，及所需资源需求的设计制作
  • 负责项目整体剧情故事、脚本，以及剧情表现相关系统规则的设计
  • 负责项目配置中所有文案性内容的填充
🔧
1.2.6 执行策划
  • 根据项目制作进度需要，协助其他专职策划完成部分设计工作
  • 熟悉项目编辑类工具，负责项目资源、素材、配置的录入、测试及修正
  • 负责基础策划文档的撰写、整理、修订等工作
  • 负责协调策划团队与其他研发业务组的沟通协作，并及时向需求责任人反馈
02 日常工作规范 会议 · 文档 · 工作管理
2.1 策划会议规范2.1
💡 2.1.1 策划设计会议
  • 会议概述：策划最主要的业务会议；项目不同设计阶段，形式和目的略有差别。固定由策划业务负责人召集、主持，并于会后跟进会议结论的执行
  • 参会人员：策划业务组全体成员；涉及项目整体、核心内容的设计会议，项目负责人共同参与
① 创意设计风暴
在一项具体设计启动之初，通常采用头脑风暴形式，各自提出针对该项设计的创意点，进行设计想法的碰撞和灵感触发。
② 设计草案论证
基于达成共识的创意点筛选，责任策划草拟设计方案，主要关注设计核心及要点，经全员讨论、质疑、反馈，进行草案充分论证。
③ 正式方案校验
经充分论证的草案，在进行必要可行性论证后，由责任策划在策划内部设计会议完整宣讲，其他成员提出查漏补缺意见，完成方案校验。
🗓 2.1.2 策划工作例会
  • 考虑项目及策划团队规模，不单独安排策划工作例会
  • 策划全体参加项目组周会，直接参与项目组当周工作布置
  • 策划作为「需求责任人」，及时汇报反馈工作进度
2.2 策划文档规范2.2
📄 2.2.1 文档规范概述 — 项目统一规范重申
  • 统一使用 Microsoft Office Professional Plus 2021 作为文档类资料编辑工具
  • 非特殊需要，所有文档类资料编辑完成后，均以 .pdf 格式输出
  • 单纯流程图、原型图等示意图内容，也可使用 .png 格式输出
  • 表格类工作资料，以 .xlsx 或 .xlsm 格式输出
规范主要针对策划对外的需求文档以及内部协作的正式文档；对个人业务草稿、设计草案无严格约束。

2.3 日常工作管理2.3
📌 2.3.1 日常工作概述
  • 业务性工作：设计元素收集、设计方案拟定、项目需求制定、项目内容配置填充等具体设计相关工作
  • 协调性工作：协调推进所负责需求的具体制作、实现相关的所有工作，并监督整个需求进度情况
📈 日常工作进度管理
  • 项目 PMS 系统：策划作为 Jira 工作流的核心，需在充分了解 Jira 工作原理的前提下，通过对具体 Jira 工作任务的管理、监控，主动积极监督并推进整个 Jira 工作流运转
  • 个人 GTD 工具：个人琐碎工作事务推荐使用 GTD 工具（推荐「滴答清单」）进行有效管理
🗄 2.3.2 日常工作存档
  • 原则上，策划日常工作内容都应在 SVN 进行存放备份
  • 存放位置：/svn/flower/doc/6. 日常工作
  • 每个成员一个文件夹，其下建立 「yyyy.mm」 形式按月子文件夹
  • 日常工作备份存档，尽可能每天工作结束后进行一次
  • 与正式需求的输出、发布互不冲突，分别进行
🔍 策划负责人、项目负责人将不定期对策划日常工作文件夹内容进行检查。
03 项目设计流程 概念设计 → 整体设计 → 具体设计
3.1 项目概念设计3.1
3.1.1 类型风格定义
根据公司研发战略、市场需求判断，以及项目题材（IP）等外部条件，兼顾团队自身制作经验、业务擅长，确定项目具体的类型、风格定义。

需全面评估外部市场需求、IP 题材特点，结合制作团队的技术实现、美术表达等各方面制作实力，最终制定包括 IP 核心元素游戏化形式、竞品分析、美术表现形式及表现水准 的产品制作方向。
3.1.2 核心概念设定
基于对产品类型、风格的初步设定，深挖项目题材（IP）相关设计元素，罗列、筛选可进行游戏化的创意点，对产品中核心功能、核心表现的概念进行设定。

可在策划团队对项目题材（IP）深度调研、挖掘后，以 创意风暴形式 进行。最终成果是在拟定产品制作方向基础上，补充完善 核心玩法、特色玩法、核心体验循环 等核心设定。
3.1.3 核心 Demo 设计
在产品制作方向、核心/特色玩法、核心体验循环设定完成的基础上，对 Demo 版本进行内容规划和需求设计。

Demo 版本定义与目的：将可能影响整个项目设计走向、类型选择、产品定位的核心内容进行验证、确认及可行性评估。在此原则下，提取 Demo 需优先实现或论证的内容，并进行核心规则及核心表现设计。
3.2 项目整体设计3.2
🏗 3.2.1 系统框架设定
设计步骤
  1. 首先：根据具体内容、实现方式、表现形式划分系统内容。可参照同类型经典项目划分方式，部分创新设计内容需独立划分系统
  2. 而后：根据各系统在项目中核心性、创新性地位差异构建基本系统框架。以核心系统为设计根本，以创新系统为设计重点，确保各系统的均衡与协调
开展方式
具体设计过程以多轮策划设计会议形式，策划团队主要成员参与系统内容梳理，由项目制作人、主策划主导进行框架设定。
🔢 3.2.2 数值结构设定
设计步骤
  1. 首先：根据项目类型确定数值分类体系（如养成数值、战斗数值、经济数值等），并确定其运转关系
  2. 其次：根据各主要系统在系统框架中的定位，划定所属的数值分类体系
  3. 最后：通过对同一数值分类体系中的各个主要系统综合考虑，设定各分类体系初步的数值结构
开展方式
系统框架基本确认后，由制作人、主策划、核心系统策划初步整理、罗列各主要系统数值关联需求（含关联方式、关联强度），交由数值策划完成初步设定。可通过 1～2 轮策划设计会议 完成该阶段设计工作。
🌍 3.2.3 世界构成设定（世界观设定）
世界观定义
项目最终完成产品所表现且能被玩家感知的游戏世界内的所有元素，都属于世界观范畴，包括：角色、场景、背景故事，以及游戏内存在的所有物品、事件等。
设计原则
世界观虽是包装性内容，却是玩家最直观看到、感知到的设定。因此必须吻合游戏设计的定位、风格、概念以及调性，需要有高度统一的设计出发点和设计诉求。
开展方式
在充分理解认知项目类型、风格及题材（IP）的前提下，首先确定设计边界；而后自大及小地对整体世界观进行设定。此过程需要一定周期补充完善，由制作人、主策划把握整体调性，内容策划具体负责。
3.3 项目具体设计3.3
⚙️ 3.3.1 具体系统设计 — 三阶段
阶段一
创意风暴
全员预备素材创意
1～2 次风暴会议
核心创意提供者任负责人
阶段二
设计草案
脑图/表单形式
1～2 次论证会议
协同程序&美术可行性论证
最终设计方案
阶段三
正式需求制作
参见「4 开发需求规范」
1 次内部需求审核会议
校验 & 审核完成
📌 草案阶段只需达到核心体验循环明确即可，文档形式不作严格要求（推荐脑图、表单）；经策划团队整体共识且完成可行性论证的方案，即为最终设计方案。
📊 3.3.2 具体数值设计
系统参数结构
  1. 根据确定的系统设计方案，与系统责任策划沟通明确对数值效果的期望及要求
  2. 在整体数值架构框架内，设计本系统参数结构，并与系统责任策划协调确认
  3. 与程序协调调整，最终确认系统参数结构
本阶段数值设计工作应当与系统正式需求制作同步，并作为正式需求中的必要内容完成输出。
数值效果调试
  1. 根据系统策划的效果预期，设计数值基础参数及关联效果运算方式
  2. 以自制测试工具（Excel 等）进行模拟测试，调试优化相关设计
  3. 在需求已实现的游戏版本中反复体验、调试，完善数值设计
💡 数值设计原则（口诀）：系统方案确定了 → 就应该有数据配置结构；有数据配置结构了 → 就应该有功能测试数据；系统功能完成了 → 就应该有正式体验数据。

模拟测试调试主要存在于设计阶段；游戏实际体验调试存在于整个设计、开发，甚至运营阶段。

由数值策划总体负责，系统责任策划提出数值期望及要求并负责验收；意见不一致时可通过策划设计会议协调或调整。
✍️ 3.3.3 具体内容设计
类别设计要点
包装类设计 根据确定的系统设计方案，结合世界观基础设定，对整个功能进行包装设计，包括：功能名称、物品名称、功能表现形式等包装内容
剧情类设计 ① 符合世界观背景基础设定，根据背景故事设计具体剧情的推进演绎
② 明确游戏剧情是一项包装属性，如何运用系统功能去表达剧情、丰富表现是重要的设计考量点
③ 设计剧情的同时，需要结合游戏美术资源的设计和应用
资源类设计 ① 界面类资源：由系统策划根据系统功能需要设计，并作为正式需求的必要部分
② 场景、角色、特效等各类资源：由内容策划负责设计，以配合整体世界观表达
③ 部分美术资源涉及功能逻辑和应用时，内容策划需与相关策划协调开展设计
由内容策划总体负责，系统责任策划提出期望及要求并负责验收内容设计成果；双方不能达成一致时，可通过策划设计会议形式进行协调或调整。
04 开发需求规范 系统功能 / 美术资源 / 数据埋点
4.1 系统功能需求4.1
4.1.1 功能概述
对该功能进行整体性简述，使阅读者快速了解该文档对应的需求，其包含的主要功能点及特殊内容，形成初步印象。同时可根据需要，简单说明该需求的设计目的、系统定位、设计思路等基础信息。
4.1.2 配置参数
主要由该需求策划人员定义配置方式及配置数据结构；如执行过程有困难，可通过与策划负责人、数值策划，甚或相关开发人员协商确定。

无论何种方式，最终确定的配置结构及说明需在需求中列明：字段名、字段类型、字段说明及配置方式说明，并与后续规则相对应。
📏 4.1.3 功能规则 — 「总-分-总-分」模式
设计方式
环节说明
总明确整体需求目的和定位
分需求项目/内容分项逐一列举，并标注多维度分类标签
总汇总各个分类维度，整理一个主要划分维度
分基于选择的主维度，将各项内容分别进行具体设定
整理步骤
  1. 将该需求涉及内容进行罗列
  2. 将所有罗列项目，按不同分类标准（维度）进行分类（标签）
  3. 根据所有项目间的层级、关联强度，决定各分类维度的优先级别
  4. 依据确认的分类维度层级，确定规则说明标题层级（1～3 个层级）
  5. 根据已划分确定的规则说明层级结构，补全各块规则的详细说明
🖱 4.1.4 交互规则
独立于功能规则，主要针对具体功能界面进行交互规则详细说明：
  • 界面信息：包括界面具体展示的信息，以及信息展示的形式、样式
  • 界面操作：包括界面操作的内容、操作的方式，以及操作的效果以及各种反馈
4.2 美术资源需求4.2
🖥 4.2.1 界面资源需求
系统功能的界面资源需求，由系统策划在系统功能设计方案确认时，以 UE 设计需求 形式交由交互策划进行交互原型设计后，以 UI 制作需求 形式提交给 UI 美术制作。
UE 设计需求 系统策划 → 交互策划
  • 交互原型：以 Axure 制作的简单线框原型图，确认交互层级和基本样式需求
  • 交互说明：简单列举说明界面需展示的信息、操作、状态，并标注必要性等级
  • 包装建议：可针对整个交互界面的整体包装建议，也可针对个别元素的包装建议
  • 形式：系统文档中图文说明，或 Jira 任务中独立的图文说明
UI 制作需求 交互策划 → UI 美术
  • 交互原型：高保真界面原型图（蓝湖），并辅以样式、控件的具体规格说明
  • 交互示意：以简单交互预览，表现界面交互逻辑及状态样式
  • 动效示意：以动画预览形式展示动效设计方案，并补充特效设计说明
  • 形式：以蓝湖为主，可辅以简单的文字说明
✅ 界面资源制作确认后，由系统策划将美术界面效果图附于系统功能文档，并补充交互规则说明。
🎨 4.2.2 其他资源需求
  • 除界面资源外，其他美术类资源在系统功能文档中需列举所需资源种类及制作规格
  • 具体需求由内容策划负责设计，并由内容策划协同美术制作人员制定标准需求清单进行提交
  • 资源需求清单位置：/svn/flower/doc/5. 美术需求
📡 4.3 数据埋点需求
  • 前期规划：系统责任策划完成系统方案设计、制作正式需求的同时，可对本系统的数据埋点需求进行简单规划；规划的埋点需求简单汇总，由数值策划统一记录
  • 后期整理：上线版本整体开发完成进入发布前准备阶段时，由数值策划负责整理本发布版本各个系统的埋点需求，并正式制作数据埋点清单，提交开发
